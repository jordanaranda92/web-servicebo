# Technical Analysis: Menú lateral fijo y colapsable

- **Fecha:** 2026-05-06
- **Identificador:** side-menu
- **Fuente:** docs/functional-analysis/2026-05-06-side-menu.md
- **Estado:** Ready for implementation

## 1) Resumen técnico

- Crear un widget shell (`SideMenuShell`) que actúe como raíz de la aplicación,
  componiendo un `Row` con el panel de navegación lateral fijo a la izquierda y
  el contenido de la sección activa a la derecha.
- El menú lateral es un widget personalizado (no un `Drawer` de Flutter) con dos
  estados de ancho: expandido (icono + texto) y colapsado (solo icono), con
  animación de transición.
- El estado del menú (índice activo + colapsado/expandido) se gestiona con un
  `Cubit` propio registrado en GetIt.
- Se crean tres features placeholder (`orders_today`, `orders_history`,
  `settings`) con la capa `presentation/pages/` mínima.
- Se actualizan el router, la DI y las traducciones i18n.
- **Áreas impactadas:** `lib/app/router/`, `lib/app/di/`,
  `lib/app/localization/`, `lib/features/home/`, tres nuevas features.
- **Riesgo general:** Bajo — no hay lógica de negocio compleja; los cambios son
  principalmente de UI y estructura de navegación.

## 2) Contexto técnico observado

- **Clean Architecture feature-first** con capas `data/`, `domain/`,

- Estado gestionado con **flutter_bloc** (BLoC/Cubit).
- DI con **GetIt** (`sl`) registrada en módulos bajo `lib/app/di/modules/`.
- i18n con **ARB** (`app_es.arb`) + generación automática (`flutter gen-l10n`).
- Tema Material 3 con design tokens centralizados en `theme_constants.dart`.

| -------------- | ----------------------------------------------------- | -------------------------------------------------------- |
| Router         | `lib/app/router/router.dart`                          | Mapa `appRoutes` con ruta `/` → `HomePage`               |
| DI             | `lib/app/di/injection.dart`                           | Registra `CoreModule` + `LocaleModule`                   |
| Main           | `lib/main.dart`                                       | `MaterialApp` con `routes: appRoutes`, landscape forzado |

- Orientación bloqueada a **landscape** (`landscapeLeft`, `landscapeRight`).
- Solo tema **light**.
- Navegación actual con **named routes** (`Map<String, WidgetBuilder>`).

## 3) Objetivo técnico

- **Qué debe cambiar:** La ruta raíz (`/`) debe dejar de apuntar a `HomePage`
  directamente y pasar a un `SideMenuShell` que contenga el menú lateral + el
  contenido de la sección activa.
- **Resultado técnico:** Un layout `Row([SideMenu, Expanded(content)])` donde
  `SideMenu` es un panel fijo y colapsable, y `content` es la página de la
  sección activa, intercambiada por un `Cubit`.
- **Limitaciones a respetar:**
  - No usar `Drawer` overlay de Flutter (es un panel fijo en el layout).
  - No usar `NavigationRail` de Material (no ofrece suficiente control sobre el
    header con logo ni la animación de colapso personalizada).
  - No introducir nuevas dependencias.
  - Respetar design tokens del tema (no hardcodear colores, tamaños, spacing).
  - Todos los textos visibles vía i18n.

## 4) Diseño técnico de la solución

### Enfoque propuesto

Un widget `SideMenuShell` (StatelessWidget con BlocBuilder) como punto de
entrada de la ruta raíz. Este widget compone:

```
Row
├── SideMenu (ancho animado: expandedWidth / collapsedWidth)
│   ├── Header (logo expandido / logo compacto)
│   ├── MenuItems (icono + texto animado con clip/fade)
│   └── ToggleButton (colapsar/expandir)
└── Expanded
    └── _pages[selectedIndex]  (contenido de la sección activa)
```

### Componentes / módulos / servicios afectados

**Nuevo Cubit: `SideMenuCubit`**

Gestiona dos estados:

- `selectedIndex` (int): índice de la sección activa (0-3).
- `isExpanded` (bool): si el menú está expandido o colapsado.

Se ubica en la capa de presentación de la feature `home` (dado que el shell de
navegación es parte de la estructura raíz de la app y `home` es su punto de
entrada natural). Alternativa válida: ubicarlo en `lib/app/` como componente de
aplicación; se recomienda la primera opción por coherencia con Clean
Architecture feature-first.

**State:**

```dart
class SideMenuState extends Equatable {
  final int selectedIndex;
  final bool isExpanded;
  // ...
}
```

**Métodos del Cubit:**

- `selectItem(int index)` — cambia `selectedIndex`.
- `toggleExpanded()` — alterna `isExpanded`.

**Nuevo widget: `SideMenuShell`**

- `StatelessWidget` que usa `BlocBuilder<SideMenuCubit, SideMenuState>`.
- Compone un `Row` con:
  - `AnimatedContainer` (o equivalente) para el panel lateral con ancho animado
    entre dos constantes.
  - `Expanded` para el contenido de la sección.
- La lista de páginas se define como un `List<Widget>` indexada:
  - `[0]` → `HomeContent` (el body actual de `HomePage` sin su propio Scaffold)
  - `[1]` → `OrdersTodayPage` (placeholder)
  - `[2]` → `OrdersHistoryPage` (placeholder)
  - `[3]` → `SettingsPage` (placeholder)

**Nuevo widget: `SideMenu`**

- Widget privado o en `widgets/` de la feature `home`.
- Recibe: `selectedIndex`, `isExpanded`, callbacks `onItemSelected`,
  `onToggleExpanded`.
- Renderiza:
  - Header con logo (asset de imagen con fallback).
  - Lista de `_SideMenuItem` con icono, texto (visible solo cuando expandido) y
    estado activo.
  - Botón de toggle en la parte inferior.
- Usa `AnimatedContainer` para la transición de ancho.
- Los textos de cada ítem se obtienen de `AppLocalizations`.

**Modificación de `HomePage`**

- `HomePage` ya no tendrá su propio `Scaffold` con `AppBar`. El `Scaffold` pasa
  al `SideMenuShell`.
- Se extrae el contenido actual del `body` de `HomePage` a un widget
  `HomeContent` (o se mantiene `HomePage` pero sin Scaffold, solo retornando su
  contenido).

### Contratos e interfaces

No se crean interfaces de dominio nuevas. El `SideMenuCubit` es puramente de
presentación (UI state), no involucra lógica de negocio ni repositorios.

### Flujo de datos o de control

1. `MaterialApp` → ruta `/` → `SideMenuShell`.
2. `SideMenuShell` lee `SideMenuCubit` vía `BlocBuilder`.
3. Tap en ítem del menú → `SideMenuCubit.selectItem(index)` → emite nuevo estado
   → `BlocBuilder` reconstruye mostrando la página correspondiente.
4. Tap en toggle → `SideMenuCubit.toggleExpanded()` → emite nuevo estado →
   `AnimatedContainer` transiciona el ancho del menú.

### Gestión de errores y validaciones

- **Logo no disponible:** El widget de logo usa `Image.asset(...)` con un
  `errorBuilder` que retorna un `SizedBox` vacío o un icono de placeholder. No
  se lanza excepción.
- **Índice fuera de rango:** El Cubit valida que el índice esté en rango
  `[0, 3]` antes de emitir.
- No hay errores de red ni persistencia involucrados.

### Consideraciones de compatibilidad o migración

- La `HomePage` actual pierde su `Scaffold` y `AppBar`. Si hay tests que
  dependan de `HomePage` encontrando un `Scaffold`, deberán actualizarse.
- La ruta `/` cambia su destino de `HomePage` a `SideMenuShell`. El
  `initialRoute` en `main.dart` sigue siendo `/`, sin impacto.

## 6) Estrategia de implementación

### Pasos

1. **Crear `SideMenuState` y `SideMenuCubit`** — Estado y lógica del menú
   lateral.
2. **Crear el widget `SideMenu`** — Panel lateral con header, ítems y toggle.
3. **Crear las páginas placeholder** — `OrdersTodayPage`, `OrdersHistoryPage`,
   `SettingsPage`.
4. **Modificar `HomePage`** — Eliminar Scaffold/AppBar, dejar solo el contenido.
5. **Crear `SideMenuShell`** — Widget shell que compone el Row(SideMenu +
   contenido).
6. **Actualizar traducciones** — Añadir claves i18n en `app_es.arb` y regenerar.
7. **Registrar DI** — Registrar `SideMenuCubit` en GetIt.
8. **Actualizar `main.dart`** — Añadir `BlocProvider<SideMenuCubit>` al
   `MultiBlocProvider`.
9. **Actualizar router** — Cambiar ruta `/` a `SideMenuShell`.

### Orden recomendado

- Pasos 1, 2, 3, 6 son independientes entre sí → pueden ejecutarse en paralelo.
- Paso 4 (modificar HomePage) antes de paso 5 (crear SideMenuShell, que la
  referencia).
- Pasos 7, 8, 9 dependen de que 1-6 existan.
- Paso 9 es el último (conecta todo).

### Dependencias entre pasos

- `SideMenuShell` (paso 5) depende de `SideMenu` (2), `SideMenuCubit` (1),
  páginas placeholder (3) y `HomePage` modificada (4).
- El router (9) depende de `SideMenuShell` (5).
- La DI (7) y `main.dart` (8) dependen del `SideMenuCubit` (1).

### Puntos delicados

- **Ancho del menú:** Definir constantes para `expandedWidth` y `collapsedWidth`
  en `theme_constants.dart` (ej: 240.0 y 72.0). No hardcodear.
- **AnimatedContainer vs. AnimatedSize:** `AnimatedContainer` es la opción más
  simple para animar el ancho. La duración recomendada es ~200-300ms con
  `Curves.easeInOut`.
- **Logo asset:** El asset del logo aún no existe. Usar un placeholder
  provisional (icono de Material o un `SizedBox`) con `errorBuilder` para evitar
  crash. Documentar como pendiente.
- **IndexedStack vs. lista directa:** Usar `IndexedStack` para preservar el
  estado de las páginas cuando el usuario navega entre secciones (evita
  reconstrucción). Si las páginas son simples placeholders, la lista directa
  también es aceptable inicialmente.
- **AppBar:** El `SideMenuShell` debe decidir si incluye un `AppBar` global o si
  cada página define la suya. Dado que el `SideMenu` ocupa el lateral izquierdo
  completo, se recomienda que cada página incluya su propia `AppBar` (o no la
  incluya si no la necesita), y el `SideMenuShell` solo contenga el `Row`. Esto
  da más flexibilidad por sección.

## 7) Estrategia de validación

### Verificación automática (tests)

- **Test unitario del `SideMenuCubit`:**
  - Estado inicial: `selectedIndex == 0`, `isExpanded == true`.
  - `selectItem(2)` → emite estado con `selectedIndex == 2`.
  - `selectItem(0)` cuando ya es 0 → no emite nuevo estado (o emite el mismo,
    idempotente).
  - `toggleExpanded()` → alterna `isExpanded`.
  - `selectItem(-1)` o `selectItem(5)` → no cambia estado (validación de rango).

- **Test de widget del `SideMenu`:**
  - Renderiza 4 ítems con los textos correctos (requiere mock de l10n).
  - El ítem activo tiene decoración diferenciada.
  - Tap en ítem invoca callback con índice correcto.
  - Tap en toggle invoca callback de toggle.

- **Test de widget del `SideMenuShell`:**
  - Renderiza `SideMenu` + contenido de la sección activa.
  - Cambio de estado del Cubit muestra la página correspondiente.

### Validación manual

- Verificar que la animación de colapso/expansión es fluida en landscape.
- Verificar que el contenido principal se reajusta al colapsar/expandir.
- Verificar comportamiento en distintos tamaños de pantalla landscape.
- Verificar que el logo placeholder/fallback se muestra sin crash si no existe
  el asset.

### Escenarios a cubrir

- Navegación entre las 4 secciones.
- Colapsar y expandir varias veces seguidas.
- Colapsar → navegar → expandir (combinación de acciones).
- Arranque de la app: menú expandido, sección Inicio activa.

### Tipo de pruebas recomendables

- **Unitarias:** `SideMenuCubit` con `bloc_test`.
- **Widget:** `SideMenu`, `SideMenuShell` con `flutter_test` + `mocktail`.
- **No se requieren:** Tests de integración, E2E ni de golden para esta
  iteración.

## 8) Riesgos, impacto y rollback

### Riesgos identificados

| Riesgo                                              | Probabilidad         | Impacto                              |
| --------------------------------------------------- | -------------------- | ------------------------------------ |
| Logo no disponible                                  | Alta (assets vacíos) | Bajo — se usa fallback               |
| Animación de ancho con jank                         | Baja                 | Bajo — ajustable con duración/curva  |
| Conflicto con scroll del contenido al cambiar ancho | Baja                 | Medio — EC-04 del análisis funcional |

### Impacto potencial

- La navegación de la app cambia fundamentalmente (de ruta única a shell con
  menú).
- `HomePage` pierde su Scaffold → cualquier test existente que busque Scaffold
  en `HomePage` fallará.

### Mitigación

- Logo: implementar `errorBuilder` desde el inicio.
- Animación: usar `AnimatedContainer` con duración conservadora (200ms).
- Scroll: el contenido está en un `Expanded` que respeta el layout de `Row`; no
  debería afectar, pero validar manualmente.
- Tests: actualizar tests de `HomePage` en el mismo paso que se modifica.

### Plan de rollback

- Revertir la ruta `/` en `router.dart` para apuntar a `HomePage`.
- Restaurar el `Scaffold` en `HomePage`.
- Eliminar `BlocProvider<SideMenuCubit>` de `main.dart`.
- Los archivos nuevos (cubit, shell, menú, placeholders) pueden dejarse sin
  afectar la app.

## 9) Suposiciones

- El `SideMenuCubit` no necesita persistir su estado entre sesiones
  (colapsado/expandido se resetea al abrir la app).
- Las páginas placeholder son `StatelessWidget` sin lógica; se reemplazarán
  cuando se implementen las features completas.
- No se requiere un `AppBar` global; cada sección gestiona su propia barra si la
  necesita.
- El logo se proveerá como asset futuro; el código incluye fallback.
- El menú se expande por defecto al iniciar la app.

## 10) Preguntas abiertas

- **PA-01 (heredada):** ¿Se dispone del asset del logo? ¿Versión compacta para
  estado colapsado? → Se implementa con fallback hasta que el asset esté
  disponible.
- **PA-02:** ¿Se prefiere `IndexedStack` (preserva estado de cada página) o
  cambio directo de widget (reconstruye al navegar)? → Se recomienda
  `IndexedStack` y se asume como decisión por defecto salvo indicación
  contraria.

## 11) Notas para implementación

- **Constantes de ancho:** Añadir `sideMenuExpandedWidth` y
  `sideMenuCollapsedWidth` en `theme_constants.dart` para evitar magic numbers.
- **Duración de animación:** Considerar añadir una constante de duración en
  `theme_constants.dart` o usar directamente `Duration(milliseconds: 200)`.
- **Orden de iconos sugerido:** `Icons.home_rounded`,
  `Icons.receipt_long_rounded`, `Icons.history_rounded`,
  `Icons.settings_rounded`.
- **Claves i18n a añadir en `app_es.arb`:**
  - `menuHome` → "Inicio"
  - `menuOrdersToday` → "Pedidos Hoy"
  - `menuOrdersHistory` → "Historial Pedidos"
  - `menuSettings` → "Ajustes"
  - `pagePlaceholderTitle` → "{section}" (con parámetro)
  - `pagePlaceholderMessage` → "Esta funcionalidad está en desarrollo"
- **No romper comportamiento existente:** La `HomePage` modificada debe seguir
  mostrando el mismo contenido visual, solo pierde el Scaffold/AppBar que pasa
  al shell.
- **DI:** El `SideMenuCubit` puede registrarse como factory (no singleton) si se
  quiere resetear al navegar, o como singleton si se quiere preservar estado. Se
  recomienda **singleton** para coherencia con el patrón del menú persistente.
- **Secuencia sugerida:** Empezar por cubit + state (testeable de forma
  aislada), luego widgets, luego conectar DI/router/main.
